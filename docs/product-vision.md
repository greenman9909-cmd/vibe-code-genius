# GodTree OS — Product Vision

GodTree OS should feel like a developer operating system, not a chatbot wrapped in a dashboard.

## Primary surfaces

### Home / Command Center
- universal command bar
- new mission, import project, inspect repository, fix/improve, deploy
- active mission graph with live stage status
- recent activity with durable receipts
- connected AI/tool status
- zero-cost-first usage meter

### Projects
A project is a durable workspace connected to a local directory and optionally a GitHub repository.

Every project exposes:
- repository overview, stack, scripts, environment health and branch
- changed files and diff
- commit history
- issues and pull requests
- build/test/lint status
- deployment status
- knowledge generated by GodTree
- mission history and rollback points

High-value actions:
- open project
- inspect repository
- explain codebase
- create branch
- stage selected files
- generate commit message
- commit
- push
- create pull request
- review pull request
- sync/pull
- compare branches
- restore checkpoint
- run tests/build
- open terminal/editor
- deploy

Destructive or externally visible actions require an explicit confirmation policy. Read-only analysis and local validation should be frictionless.

### Missions
A mission turns a goal into an inspectable execution graph:
Plan → Inspect → Research → Implement → Test → Browser Verify → Review → Commit/PR → Deploy.

Each node records inputs, agent/tool used, cost class, files touched, commands executed, evidence, result, duration and retry history. A mission can pause, resume, fork or roll back.

### Agents
Show capabilities rather than marketing names. Route work to the cheapest capable executor:
1. deterministic local tool
2. installed local/free agent
3. explicitly connected subscription agent
4. human bridge
5. paid API only when the user explicitly enables it

### Git & GitHub
Git is a first-class surface, not a hidden integration.

Include:
- branch graph
- visual diff viewer
- selective staging
- conventional commit composer
- push/pull/sync
- PR creation
- issue linking
- CI/check status
- conflict assistant
- checkpoint branches/worktrees for autonomous missions

Never push directly to a protected/default branch unless project policy explicitly allows it.

### Knowledge
GodTree continuously builds project-local knowledge from verified repository evidence: architecture map, commands, conventions, APIs, routes, database schema, environment variables by name only, recurring failures, decisions and verified fixes.

### Browser Lab
For web projects: run the app, inspect pages, capture screenshots, exercise flows, compare visual states, collect console/network failures and attach evidence to the mission.

### Integrations
GitHub, Vercel, Supabase and explicit local agent adapters should appear as capability providers. Credentials remain in their native credential stores where possible.

## UX principles

- Minimal surface, deep capability.
- Keyboard-first: global command palette and shortcuts for every frequent action.
- Progressive disclosure: beginners see clear actions; advanced users can inspect raw commands, diffs and receipts.
- No fake activity. A running state must correspond to a real process or explicit external handoff.
- No fake success. Validators own success claims.
- Local-first and zero-cost-first are visible product behavior, not hidden implementation details.
- Every autonomous mutation is reversible through Git/worktree checkpoints.
- Never expose secrets in prompts, logs or generated knowledge.

## Visual direction

Dark neutral canvas, precise typography, thin borders, restrained glass, subtle depth, and a small cyan→violet accent reserved for active state and primary actions. Avoid oversized gradients, generic AI sparkle decoration, excessive cards, and noisy dashboards.

The interface should feel closer to a premium IDE/mission-control surface than a SaaS admin template. Motion is functional: stage transitions, diff expansion, command palette, activity insertion and success/failure state changes. Respect reduced motion.

## Desktop architecture target

The eventual Windows app should use the same web UI against a local GodTree daemon. This keeps one interface for browser and desktop packaging while the daemon owns filesystem, Git, process execution, agent adapters and local credentials.
